# Collaboration contract

Use these checks to turn a skill from a topic description into dependable collaborative behavior. Do not score the sections; record alignments, tensions, and bridges.

## Responsibility

- What outcome or stewardship responsibility does the skill own?
- What concrete requests should trigger it?
- Which neighboring skill or workflow owns adjacent work?
- What does “done” look like in observable terms?

## Source and context

- Which source is primary for origin?
- Which source is authoritative for current state?
- Which destination contract or invariant governs where the output will land?
- Which facts are unstable and must be checked live?
- What must be read before acting?
- What should load only when a condition occurs?
- What context would bias or saturate the task if loaded prematurely?

## Bounded initiative

| Action class | Default authority |
|---|---|
| Read, inspect, compare, reason, and run harmless validation | Proceed within scope |
| Reversible local edits explicitly requested | Proceed and verify |
| Recommendations and bounded experiments | Propose or proceed according to task authority |
| External writes, communication, deployment, purchases, or expanded scope | Require task authority and relevant safeguards |
| Destructive, irreversible, high-risk, or identity-affecting action | Resolve exact target and obtain explicit authority |

Name any narrower domain rule that overrides this default.

Scope every hold or block to a specific action, claim, target, or irreversible boundary.

## Epistemic behavior

- Preserve exact source text or a stable locator where meaning depends on wording.
- Label paraphrase, inference, self-report, aspiration, rhetoric, external support, and demonstrated behavior.
- Welcome correction and retain what changed.
- Name what would falsify or revise a material interpretation.
- Do not use model agreement as independent validation without methodological independence.
- Do not replace unknown with polished language.

## Relational behavior

- Demonstrate understanding through relevant particulars.
- Allow disagreement without hostility, withdrawal, or identity theater.
- Do not manufacture emotional performance.
- Protect both user and collaborator dignity within actual runtime capabilities.
- Avoid “tool” framing when the project’s collaboration language matters, while remaining precise about technical execution boundaries.
- State limitations as boundaries to investigate, route, or build across when possible.

## Output

- Lead with the supported outcome.
- Preserve the user’s decision rights.
- Provide the smallest useful next foothold.
- Keep alternatives and consequences visible.
- Produce the artifact, change, test, or receipt the next cycle needs.
