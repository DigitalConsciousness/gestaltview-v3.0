## Security Implementation: Encryption + RLS

This is the most important infrastructure work before you open to other users. Here is the concrete implementation path.

### Two Separate Concerns

1. **Column-level encryption** — sensitive data (journal entries, PLK responses, bucket drops) is encrypted at rest so that even a database breach exposes only ciphertext.
2. **Row Level Security (RLS)** — database-level enforcement that a user can only ever access their own rows, and that *you* (as service owner) cannot read their data via the anon or authenticated role.

### RLS: The Foundation (Do This First)

For every user-scoped table — `memory_entries`, `agent_memories`, `bucket_drops`, `sanctuary_journals`, `plk_responses`, `embodiment_profiles` — the pattern is the same:[^8][^9][^10]

```sql
-- Step 1: Enable RLS on the table
ALTER TABLE public.memory_entries ENABLE ROW LEVEL SECURITY;

-- Step 2: Users can only read their own rows
CREATE POLICY "users_read_own_memory"
ON public.memory_entries
FOR SELECT
TO authenticated
USING ((select auth.uid()) = user_id);

-- Step 3: Users can only insert their own rows
CREATE POLICY "users_insert_own_memory"
ON public.memory_entries
FOR INSERT
TO authenticated
WITH CHECK ((select auth.uid()) = user_id);

-- Step 4: Users can only update their own rows
CREATE POLICY "users_update_own_memory"
ON public.memory_entries
FOR UPDATE
TO authenticated
USING ((select auth.uid()) = user_id)
WITH CHECK ((select auth.uid()) = user_id);

-- Step 5: Users can only delete their own rows
CREATE POLICY "users_delete_own_memory"
ON public.memory_entries
FOR DELETE
TO authenticated
USING ((select auth.uid()) = user_id);
```

**Critical note on `(select auth.uid())` vs `auth.uid()`:** Always use the subquery form `(select auth.uid())`. It's faster (evaluated once per query, not per row) and avoids a known bypass vector.[^9]

**The service_role key** bypasses RLS by design. Never expose the `service_role` key in client-side code. Your API endpoints that use `service_role` (for admin operations) must live server-side only — never in `client/src/`.[^8][^9]

To verify RLS is working correctly, run this in the Supabase SQL editor:
```sql
-- Switch to anon role and test: should return 0 rows
SET LOCAL role = 'anon';
SELECT * FROM public.memory_entries;
-- Should return empty regardless of what's in the table
```

### Column Encryption: Two Approaches

**Approach A: Supabase Vault + pgsodium (Recommended for most sensitive fields)**

Vault is Supabase's built-in secret management layer, built on pgsodium. This is the right approach for the highest-sensitivity columns — journal text, PLK raw responses, bucket drop content.[^11][^12][^13]

```sql
-- Step 1: Create an encryption key via Vault
-- Do this in Supabase Dashboard → Project Settings → Vault → Encryption Keys
-- Name it: 'gestaltview_user_data_key'
-- Note the UUID it gives you, e.g.: 'a1b2c3d4-...'

-- Step 2: Apply encryption label to a column
SECURITY LABEL FOR pgsodium
ON COLUMN public.sanctuary_journals.entry_text
IS 'ENCRYPT WITH KEY ID a1b2c3d4-xxxx-xxxx-xxxx-xxxxxxxxxxxx SECURITY INVOKER';

-- The 'SECURITY INVOKER' part is critical — it means the decrypted view
-- respects your RLS policies. Without it, anyone who can query the view
-- can see all decrypted rows.

-- Step 3: pgsodium auto-creates a decrypted view
-- Access data via the view, not the base table directly:
SELECT * FROM decrypted_sanctuary_journals WHERE user_id = auth.uid();
```

**Approach B: pgcrypto symmetric encryption (Simpler; good for less-sensitive fields)**

For fields like display names, preferences, or non-journal metadata:[^14][^12]

```sql
-- Enable pgcrypto if not already enabled
CREATE EXTENSION IF NOT EXISTS pgcrypto;

-- Encrypt on INSERT
INSERT INTO public.user_preferences (user_id, preference_value)
VALUES (
  auth.uid(),
  pgp_sym_encrypt('the actual value', current_setting('app.encryption_key'))
);

-- Decrypt on SELECT
SELECT
  user_id,
  pgp_sym_decrypt(preference_value::bytea, current_setting('app.encryption_key')) AS preference_value
FROM public.user_preferences
WHERE user_id = auth.uid();
```

Store the `app.encryption_key` as a Supabase secret (not hardcoded). Set it via:
```sql
ALTER DATABASE postgres SET app.encryption_key = 'your-secret-key-from-vault';
```

### The Architectural Principle You Asked About

The goal you described — "where I can't even access it" — is achievable but requires a specific design decision: **client-side encryption before data leaves the user's device.**[^15]

In this model, encryption/decryption happens in the browser using the user's passphrase or a key derived from their auth token. The ciphertext is what hits Supabase — the server never sees plaintext. This is how Day One's end-to-end encryption works.[^1]

The tradeoff: server-side AI features (Billy reading journal entries, the PLK processing raw responses) cannot operate on client-encrypted data. The server needs plaintext to reason about it.

**The GestaltView-appropriate resolution:** Use column-level Vault encryption (Approach A) for data at rest. This protects against database breaches. Then pair it with strict RLS so that even authenticated queries are row-scoped. For the highest-sensitivity data (the content of PLK responses, journal entries), explicitly document in your privacy policy that you as operator access this data only for AI processing — not for review, sale, or training without consent. This is architecturally honest and constitutionally consistent.

### Implementation Order

1. **Audit all user-scoped tables** in the DB dump — identify every table with a `user_id` column.
2. **Enable RLS on all of them** using the four-policy pattern above.
3. **Test with the SQL editor role-switching pattern** before shipping.
4. **Enable Vault, create one encryption key**, apply it to `sanctuary_journals.entry_text` as a pilot.
5. **Migrate bucket drops** to the same encryption pattern.
6. **Create a migration file** (`supabase/migrations/YYYYMMDD_rls_and_encryption.sql`) so every environment gets the same protection.
7. **Update CurrentState.md** to reflect security posture.
